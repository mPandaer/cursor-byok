先看结论

cursor-byok 不把 API Key 写进 Cursor，也不要求 Cursor 直接理解你的上游服务。它在本机建立一个模型网关：Cursor 选择模型，网关查配置，Provider 才注入密钥。

输入Cursor

发送 Cursor 私有协议和所选模型 ID。

model_hash
接管本地 HTTPS 代理

拦截指定 cursor.sh 路径，改写到本机服务。

CursorRelay
运行Agent Runtime

管理会话、上下文、工具调用和多轮 Run。

RunEngine
适配Provider Adapter

把统一请求翻译成上游协议，并注入 API Key。

ProviderRouter
输出你的模型服务

返回 SSE；事件再被投影回 Cursor。

ModelEvent
关键判断： API Key 的真实使用点在 Provider 层。Cursor 看到的是本地模型 ID，例如 a81f3c2d9e4b...；上游看到的才是 Authorization: Bearer ... 或 x-api-key: ...。

架构分层

目录就是架构：桌面端负责管理，本地 Rust 服务负责协议、运行时和上游适配。

cursor-byok/
├── apps/desktop/src/              # React 管理界面
├── apps/desktop/src-tauri/        # Tauri 生命周期与窗口
├── server/src/app.rs              # 组合根：组装所有后端模块
├── server/src/control/            # 管理面：模型、设置、测试
├── server/src/store/              # SQLite 持久化
├── server/src/local_app/          # CA、TLS 代理、Cursor settings
├── server/src/api/cursor/         # Cursor 协议入口
├── server/src/cursor/              # Cursor 会话与 Agent Runtime
├── server/src/run/                 # 通用 Run 循环与工具轮次
├── server/src/provider/            # OpenAI / Anthropic 适配器
├── server/src/model/               # 统一模型、消息、事件表示
└── server/src/api/byok/            # 独立 OpenAI / Anthropic 兼容入口

管理面

React 通过 /__byok-api__/api/* 配置模型和启停 Cursor 接管。它不参与模型生成。

数据面

Cursor 的 BidiAppend、RunSSE 进入本地 Runtime，负责真正的 Agent 生命周期。

适配面

Provider::stream 是统一接缝，隐藏 OpenAI、Anthropic 的请求体、Header 和 SSE 差异。

例子：保存一个自定义 Responses 模型

假设用户填写一个 OpenAI-compatible 服务，使用 Responses API。

用户填写的配置

{
  "display_name": "我的 GPT",
  "type": "openai",
  "base_url": "https://llm.example.com",
  "use_full_url": false,
  "api_key": "sk-acme-example",
  "model_id": "acme-gpt",
  "openai_endpoint": "/v1/responses"
}

系统得到的上游请求

POST https://llm.example.com/v1/responses
Authorization: Bearer sk-acme-example

{
  "model": "acme-gpt",
  "input": [...],
  "stream": true
}
UI 产生 ModelInput

CursorModelEditor.tsx 收集地址、协议、API Key 和模型名称。

Control API 接收配置

control/mod.rs 将 POST /__byok-api__/api/models 路由到模型 Handler。

Store 校验并持久化

store/models.rs 调用规范化、生成 hash，并写入 SQLite 的 model_configs。

Cursor 只获得模型 ID

model_catalog.rs 把模型 hash 和显示信息追加到 Cursor 模型列表。

03.1 配置、接管与模型发现

sequenceDiagram
    autonumber
    actor User as 用户
    participant UI as React UI
    participant Control as Control API
    participant Store as SQLite Store
    participant Harness as CursorHarness
    participant Proxy as 本地 TLS Proxy
    participant Cursor as Cursor

    User->>UI: 填写 base_url / API Key / model_id
    UI->>Control: POST /__byok-api__/api/models
    Control->>Store: normalize_model_input
    Store->>Store: 生成 model_hash
    Store-->>Control: 保存 ModelConfig
    Control-->>UI: 返回模型配置

    User->>UI: 初始化 CA 并启用 Cursor 接管
    UI->>Control: POST ca/initialize
    Control->>Harness: initialize_ca()
    Harness-->>UI: CA Ready
    UI->>Control: PUT harness/cursor/enabled
    Control->>Harness: enable()
    Harness->>Proxy: 启动本地 MITM Proxy
    Harness->>Cursor: 写入 http.proxy / settings

    Cursor->>Proxy: 请求 AvailableModels
    Proxy->>Control: 改写到本地 backend
    Control->>Store: 读取 model_configs
    Control-->>Proxy: 追加本地模型 hash
    Proxy-->>Cursor: 官方模型 + 自定义模型列表

接管路径只拦截指定的 cursor.sh 请求；其他请求仍可转发到 Cursor 官方 upstream。

03.2 一次 Agent 请求：从 Cursor 到上游模型

sequenceDiagram
    autonumber
    actor User as 用户
    participant Cursor as Cursor
    participant Proxy as CursorRelay
    participant Handler as Bidi / RunSSE Handler
    participant Runtime as ConversationRuntime
    participant Engine as RunEngine
    participant Router as ProviderRouter
    participant Store as SQLite Store
    participant Adapter as OpenAiResponsesProvider
    participant Upstream as 自定义模型 API

    User->>Cursor: 选择“我的 GPT”并发送问题
    Cursor->>Proxy: BidiAppend(model_id=model_hash)
    Proxy->>Handler: 改写请求到本地 backend
    Handler->>Store: 查询 model_hash
    Store-->>Handler: 找到 ModelConfig
    Handler->>Runtime: 选择 local_byok 路由
    Runtime->>Runtime: 解码请求、恢复会话、编译 Prompt
    Runtime->>Engine: PreparedRun
    Engine->>Router: Provider::stream(ModelInvocation)
    Router->>Store: 读取完整 ModelConfig
    Store-->>Router: api_key + request_url + provider_type
    Router->>Adapter: 构造 ProviderConfig
    Adapter->>Upstream: POST /v1/responses + Bearer API Key
    Upstream-->>Adapter: SSE response.output_text.delta
    Adapter-->>Router: ModelEvent::TextDelta
    Router-->>Engine: 统一事件流
    Engine-->>Runtime: 文本 / Tool Call / Usage / Done
    Runtime-->>Proxy: Cursor protobuf / Connect frames
    Proxy-->>Cursor: RunSSE 流式输出
    Cursor-->>User: 显示答案或执行工具

    opt Cursor 返回 Tool Result
      Cursor->>Proxy: BidiAppend(tool result)
      Proxy->>Runtime: 继续同一个 conversation / Run 生命周期
      Runtime->>Engine: 再次进入 Provider 调用循环
    end

API Key 的单一使用点是 Adapter 发往上游的请求；Cursor 请求中的认证信息不会被直接透传为上游模型密钥。

05 /

最重要的深模块

从架构阅读角度，先理解这些接口，再进入具体协议细节。

Provider::stream

它是上层 Runtime 与上游模型协议之间的接缝。上层只交付 ModelInvocation，不需要知道不同 Provider 的 JSON、Header 和 SSE。

Leverage： 一个统一接口支持多个上游协议。

TransportRegistry

它把一个 Cursor request_id 绑定到本地或官方路由，并管理本地 Transport 的生命周期。

Locality： 路由判断集中在 Cursor 协议入口。

ModelConfig

它把用户配置的地址、协议、Key、模型 ID 和生成参数聚合为一个可持久化的模型通道。

删除测试： 删除它会把配置复杂度重新散落到每个调用者。

ModelEvent

它把 OpenAI 和 Anthropic 的不同流式事件归一成文本、思考、工具、用量和完成事件。

测试面： 上层 Runtime 可以围绕统一事件测试，而不必伪造供应商 SSE。

安全边界与容易误读的地方

阅读代码时，把“网关自己的认证 Key”和“上游模型 Key”严格分开。

API Key 的存储现状

当前代码把模型 API Key 直接写入 SQLite 的 model_configs.api_key 字段；UI 只是用秘密输入框隐藏显示，并不等于加密存储。

查看写入与读取 · 查看序列化结构

两类 Key

  • 模型 API Key：用户配置，Provider 用它认证上游模型服务。
  • 外部 API Key：/byok/v1 的调用者用它认证本地网关。
  • Cursor 账号凭据：本地接管逻辑单独处理，不等于模型 API Key。
不要把这两条链混在一起： Cursor 桌面接管走的是 Cursor 私有协议和完整 Agent Runtime；/byok/v1 走的是 OpenAI / Anthropic JSON 兼容入口。它们共享 Store 和 Provider，但入口、模型 ID 语义和输出协议不同。
一句话回顾： React 保存配置 → Rust 写入 SQLite → 本地 CA/代理接管 Cursor → Cursor 用 model_hash 选路 → ConversationRuntime 和 RunEngine 执行 Agent → Provider Adapter 读取 API Key 并调用上游 → ModelEvent 再被投影回 Cursor。
